Hello, Playbook

A repo that builds

Every project starts the same way: a manifest that names it, and one file that runs. Nothing else has earned its place yet.

💾 Cargo.toml · L1–L9 · step 001 of hello-playbook · diff · browse

[package]
name = "hello-playbook"
version = "0.1.0"
edition = "2021"
rust-version = "1.95"
license = "MIT OR Apache-2.0 OR GPL-3.0-or-later"

[dependencies]

# bower:begin lints
# bower:end lints

$> git checkout step-001-cargo-init

The two comment lines at the bottom are a region marker. They mark a hole in the file that a later chapter will fill, and they are stripped out before the file reaches the repository. Chapter 3 fills this one.

💾 src/main.rs · L1–L3 · step 001 of hello-playbook · diff · browse

fn main() {
    println!("Hello, world!");
}

$> git checkout step-001-cargo-init

Both blocks above carry step="cargo-init", so they land in one commit. That is right: a manifest without a source file is not a state of the project anyone would want to check out.

Running it

This step writes no files. op="none" declares a commit that exists only to mark a moment in the narrative — here, the moment you can first run the thing. The command is:

$ cargo run
Hello, world!

That fence has no directive above it, so Bower ignores it. Only fenced blocks introduced by a <!-- bower … --> comment become code in the repository.

The gate

One command has to mean "check everything". In these books that command is make ayce — all your code, evaluated — and its meaning never varies from project to project. What varies is what it depends on, and that list grows as the book does.

💾 Makefile · L1–L14 · step 003 of hello-playbook · diff · browse

.DEFAULT_GOAL := ayce

# bower:begin help
# bower:end help

# bower:begin gate
GATE := build

build:
	cargo build --workspace

.PHONY: build
# bower:end gate

ayce: $(GATE)
	@echo "ayce — all your code, evaluated"

.PHONY: ayce

$> git checkout step-003-makefile

The GATE variable lives inside the region, which is the whole trick. Later chapters replace the region wholesale and the ayce target picks up the new prerequisites without ever being edited again.

💾 Makefile · L3–L8 · step 004 of hello-playbook · diff · browse

help:
	@echo "ayce   run the whole gate"
	@echo "build  compile the workspace"
	@echo "help   this list"

.PHONY: help

$> git checkout step-004-make-help

op="region" replaces the text between the two help markers and leaves the rest of the file alone. The page shows you five lines; the repository gets the whole Makefile. Note that the block does not repeat the marker lines — they stay in the file, waiting for the next edit.

Lints and format

Formatting and linting are not taste. They are the cheapest possible tests: they run in a second and they catch a class of mistake before a human ever reads the diff. So they belong in the gate, and the gate belongs in one command.

Pin the format

💾 rustfmt.toml · L1–L3 · step 005 of hello-playbook · diff · browse

# Only max_width is set. Everything else is rustfmt's default on purpose —
# a config file full of overrides is a config file nobody can read.
max_width = 100

$> git checkout step-005-rustfmt

Pin the toolchain

💾 rust-toolchain.toml · L1–L3 · step 006 of hello-playbook · diff · browse

[toolchain]
channel = "1.95.0"
components = ["clippy", "rustfmt"]

$> git checkout step-006-toolchain

Anyone who clones this repository gets that exact compiler, with those exact components, without being told to install anything. The version appears again in .tool-versions in chapter 6, and the two must always agree.

Fill the lints region

💾 Cargo.toml · L10–L16 · step 007 of hello-playbook · diff · browse

[lints.rust]
unsafe_code = "forbid"

[lints.clippy]
pedantic = { level = "warn", priority = -1 }
unwrap_used = "warn"
expect_used = "warn"

$> git checkout step-007-lints

This is the hole chapter 1 left open. The priority = -1 is not decoration: without it, pedantic as a lint group would override the individual lints listed after it.

Put them in the gate

💾 Makefile · L10–L21 · step 008 of hello-playbook · diff · browse

GATE := build fmt lint

build:
	cargo build --workspace

fmt:
	cargo fmt --all --check

lint:
	cargo clippy --workspace --all-targets -- -D warnings

.PHONY: build fmt lint

$> git checkout step-008-gate-fmt-clippy

--check rather than a plain cargo fmt, and -D warnings rather than a plain clippy: a gate that quietly fixes things is not a gate. It must fail.

Tests, and failing on purpose

A test that has never failed has never been tested. This chapter writes one that fails, commits it in that state, and fixes it in the next commit — so the failure is a real, tagged, checkoutable state of the repository rather than something that happened off-camera.

A library to test

💾 src/lib.rs · L1–L7 · step 009 of hello-playbook · diff · browse

//! A greeting, and nothing else.

// bower:begin mods
// bower:end mods
// bower:begin greet
/// Build a greeting for `name`.
#[must_use]
pub fn greet(name: &str) -> String {
    format!("Hello, {name}!")
}
// bower:end greet

$> git checkout step-009-greet-lib

The mods region is empty and has no blank line around it. Its blank line will arrive as part of its contents later, so that emptying the region again does not leave a double blank line behind — which the formatter, installed in chapter 3, would reject.

💾 src/main.rs · L1–L5 · step 009 of hello-playbook · diff · browse

use hello_playbook::greet;

fn main() {
    println!("{}", greet("world"));
}

$> git checkout step-009-greet-lib

op="replace" writes a whole new file over the old one. Both blocks share step="greet-lib", so extracting the function and rewiring the binary are one commit — the repository never passes through a state where main.rs refers to something that is not there yet.

A test that passes

💾 src/lib.rs · L8–L17 · step 010 of hello-playbook · diff · browse


// bower:begin tests
#[cfg(test)]
mod tests {
    use super::greet;

    #[test]
    fn greet_uses_the_name() {
        assert_eq!(greet("world"), "Hello, world!");
    }
}
// bower:end tests

$> git checkout step-010-greet-test

op="append" adds to the bottom of a file without repeating its top. The block opens with a blank line, which is how the separating blank line gets there.

A test that fails

💾 src/lib.rs · L18–L21 · step 011 of hello-playbook · diff · browse

#[cfg(test)]
mod tests {
    use super::greet;

    #[test]
    fn greet_uses_the_name() {
        assert_eq!(greet("world"), "Hello, world!");
    }

    #[test]
    fn greet_ignores_stray_whitespace() {
        assert_eq!(greet("  world  "), "Hello, world!");
    }
}

$> git checkout step-011-test-that-fails

Your turn: Make the test pass

Fork the repository, then:

git clone https://github.com/abstecker/hello-playbook.git   # or your fork
git checkout step-011-test-that-fails
cargo test

Green means you did it. The answer is the next step.

Two things are happening here.

expect="test_fail" declares that this commit's tests are supposed to fail. That is a promise the toolchain checks: when the replay layer builds this repository it runs the tests at this step and treats a pass as the error.

The bower:show markers decide what you just read. The block above contains the whole test module, because the repository needs the whole file — but only the new test was printed on the page. The markers never reach the repository.

The exercise key is the third thing. It marks this step as a place to stop reading and start typing: the box under the code above tells you how to fork the repository, check out exactly this commit, and run the tests yourself. The next section is one answer, and it stays folded until you open it.

The fix

Show the answer

💾 src/lib.rs · L3–L7 · step 012 of hello-playbook · diff · browse

/// Build a greeting for `name`, ignoring stray whitespace.
#[must_use]
pub fn greet(name: &str) -> String {
    format!("Hello, {}!", name.trim())
}

$> git checkout step-012-test-that-passes

The fix is in a different region of the same file. That is the point of regions: the test module and the function it tests grow independently, and each edit shows only itself.

Code that does not compile

💾 src/scratch.rs · L1–L6 · step 013 of hello-playbook · diff · browse

// bower:begin scratch
/// Deliberately wrong: a string literal is not a `u32`.
#[must_use]
pub fn answer() -> u32 {
    let n: u32 = "42";
    n
}
// bower:end scratch

$> git checkout step-013-wont-compile

💾 src/lib.rs · L3–L4 · step 013 of hello-playbook · diff · browse

pub mod scratch;

$> git checkout step-013-wont-compile

The second block is not decoration. A file that no module declaration points at is never compiled, so a compile_fail in an undeclared file would be a lie about the toolchain. Declaring the module and writing the broken code are one commit, and that commit genuinely does not build.

Notice the blank line at the end of that block. That is the separator promised earlier — it belongs to the region, not to the file around it.

The repair

💾 src/scratch.rs · L1–L5 · step 014 of hello-playbook · diff · browse

/// Parse the text, and fall back to zero when it is not a number.
#[must_use]
pub fn answer() -> u32 {
    "42".parse().unwrap_or_default()
}

$> git checkout step-014-scratch-fixed

unwrap_or_default rather than unwrap: chapter 3 set unwrap_used = "warn", and the gate turns warnings into failures.

Supply chain

Your code is a small fraction of what you ship. The rest arrives from a registry, written by people you will never meet, and it changes underneath you. Two tools watch it, and one script gives them a single name.

Rules for dependencies

💾 deny.toml · L1–L11 · step 015 of hello-playbook · diff · browse

[advisories]
version = 2

[licenses]
version = 2
# Exactly the licences this project actually needs. A longer list is not
# safer — it is a longer list of things you have stopped checking.
allow = ["Apache-2.0", "GPL-3.0-or-later", "MIT"]

[bans]
multiple-versions = "warn"

$> git checkout step-015-deny-toml

One name for "scan"

💾 bin/security-scan · L1–L7 · step 016 of hello-playbook · diff · browse

#!/usr/bin/env bash
# One definition of "scan". The Makefile calls this; so does CI. When the
# scan changes, it changes in one place.
set -euo pipefail

cargo audit
cargo deny check advisories bans licenses sources

$> git checkout step-016-security-scan

set -euo pipefail is not boilerplate. Without it a failing cargo audit in the middle of the script would be shrugged off and the gate would pass while the advisory stood.

Into the gate

💾 Makefile · L10–L27 · step 017 of hello-playbook · diff · browse

GATE := build fmt lint test audit

build:
	cargo build --workspace

fmt:
	cargo fmt --all --check

lint:
	cargo clippy --workspace --all-targets -- -D warnings

test:
	cargo test --workspace

audit:
	./bin/security-scan

.PHONY: build fmt lint test audit

$> git checkout step-017-gate-test-audit

The tests written in chapter 4 join the gate here, alongside the scan. ayce itself has not been edited since chapter 2 — it never needs to be, because its prerequisite list lives inside the region.

CI

CI does not need its own idea of what "good" means. It has one job: check out the code, install the toolchain, and run the same gate you run locally.

One version, declared once more

💾 .tool-versions · L1–L1 · step 018 of hello-playbook · diff · browse

rust 1.95.0

$> git checkout step-018-tool-versions

This has to agree with rust-toolchain.toml from chapter 3. Two places that name a version are two places that can disagree, so the rule in these books is that every version-declaring file is updated together, always.

The workflow

💾 .github/workflows/ci.yml · L12–L18 · step 019 of hello-playbook · diff · browse

# ... 11 lines elided — full file: https://github.com/abstecker/hello-playbook/blob/step-019-ci-workflow/.github/workflows/ci.yml
      - uses: actions/checkout@v7
      - uses: dtolnay/rust-toolchain@stable
        with:
          components: clippy, rustfmt
      - uses: taiki-e/install-action@cargo-audit
      - uses: taiki-e/install-action@cargo-deny
      - run: make ayce

$> git checkout step-019-ci-workflow

Two of those references name a version and one names a thing. actions/checkout is pinned to a major, resolved when this chapter was written. But dtolnay/rust-toolchain@stable and taiki-e/install-action@cargo-audit are not versions at all — stable and cargo-audit name what you want, and the action resolves it. Those are copied exactly and never "updated".

The last line is the whole argument. CI runs make ayce and nothing else. There is no second list of checks to drift out of step with the first.

Clearing the scratch

The broken module did its job in chapter 4 and has no reason to stay. This directive has no code block after it — op="delete" names a file and removes it, and the paragraph you are reading is what stops the next fence from being mistaken for its contents.

Deleting the file is not enough on its own. src/lib.rs still declares the module, and a declaration pointing at nothing does not compile, so the same commit empties the mods region:

$> git checkout step-020-drop-scratch

That block really is empty. The region returns to the state chapter 4 created it in, and the file goes back to having exactly one blank line where the module declaration used to be.
