Hello, Playbook

Talk to it

Every chapter so far has shown you code and what it printed. This one lets you type at it. The greeter learns to answer one line at a time, and the same answer is given in two places: a terminal, and this page.

One line in, one reply out

💾 src/session.rs · L1–L36 · step 026 of hello-playbook · diff · browse

//! One line in, one reply out: the seam every shell drives.

use crate::greet;

/// A conversation with the greeter.
#[derive(Debug, Default)]
pub struct Session;

impl Session {
    /// A new conversation.
    #[must_use]
    pub fn new() -> Self {
        Self
    }

    /// Answer one line: greet the name on it, or the world if it is blank.
    pub fn eval(&mut self, line: &str) -> String {
        let name = line.trim();
        greet(if name.is_empty() { "world" } else { name })
    }
}

#[cfg(test)]
mod tests {
    use super::Session;

    #[test]
    fn a_name_is_greeted() {
        assert_eq!(Session::new().eval("Ada"), "Hello, Ada!");
    }

    #[test]
    fn a_blank_line_greets_the_world() {
        assert_eq!(Session::new().eval("  "), "Hello, world!");
    }
}

$> git checkout step-026-session

eval reads nothing and prints nothing. It takes a line and returns a line. That is the whole point of it: whatever drives it — a terminal, a test, a web page — only has to hand it text and show what comes back. None of them can answer differently, because none of them answers at all.

It takes &mut self although it keeps nothing yet. A conversation that remembers what was said needs it, and changing the signature later would change every shell.

A terminal to type in

//! Type a name, press Enter, and the greeter answers. Ctrl-D ends it.

use hello_playbook::Session;

fn main() -> std::io::Result<()> {
    let mut session = Session::new();
    for line in std::io::stdin().lines() {
        println!("{}", session.eval(&line?));
    }
    Ok(())
}

The same code, in this page

A browser cannot run that loop, but it can run Session. Compiled to WebAssembly, with three attributes that say what JavaScript may call, the type from the start of this chapter becomes something a page can hold.

//! One line in, one reply out: the seam every shell drives.

use crate::greet;

/// A conversation with the greeter.
#[cfg_attr(feature = "wasm", wasm_bindgen::prelude::wasm_bindgen)]
#[derive(Debug, Default)]
pub struct Session;

#[cfg_attr(feature = "wasm", wasm_bindgen::prelude::wasm_bindgen)]
impl Session {
    /// A new conversation.
    #[cfg_attr(feature = "wasm", wasm_bindgen::prelude::wasm_bindgen(constructor))]
    #[must_use]
    pub fn new() -> Self {
        #[cfg(feature = "wasm")]
        console_error_panic_hook::set_once();
        Self
    }

    /// Answer one line: greet the name on it, or the world if it is blank.
    pub fn eval(&mut self, line: &str) -> String {
        let name = line.trim();
        greet(if name.is_empty() { "world" } else { name })
    }
}

#[cfg(test)]
mod tests {
    use super::Session;

    #[test]
    fn a_name_is_greeted() {
        assert_eq!(Session::new().eval("Ada"), "Hello, Ada!");
    }

    #[test]
    fn a_blank_line_greets_the_world() {
        assert_eq!(Session::new().eval("  "), "Hello, world!");
    }
}

$> git checkout step-028-repl-wasm

Every attribute is behind cfg_attr(feature = "wasm", …). Without the feature the crate is exactly what it was, and the terminal shell does not pull in anything it does not use.

The one new line in new is for the day something goes wrong. A panic in a terminal prints its message and where it happened. A panic in WebAssembly prints unreachable, and nothing else, unless something was told to keep the message: console_error_panic_hook does that, once, the first time a session starts. The page shows the message in place of a reply, and closes the prompt, because a module that has panicked cannot be trusted with another line.

The feature, and the two dependencies it turns on:

[dependencies.console_error_panic_hook]

$> git checkout step-028-repl-wasm

cdylib is the kind of library a WebAssembly module is; rlib keeps the ordinary one, which the example and the tests link.

The compiler needs the target installed. Naming it in the pinned toolchain means anyone who clones the repository gets it the first time they build:

$> git checkout step-028-repl-wasm

And one more thing changes, because chapter 5 meant it. Until now cargo deny has checked the dependencies of the default build, and that was every dependency there was. An optional one is only in the graph when its feature is on, so the gate would never look at wasm-bindgen. One table fixes that, and the first thing it finds is a licence: wasm-bindgen builds its attributes with syn, and syn reads identifiers with unicode-ident, which carries the Unicode licence as well as MIT or Apache.

💾 deny.toml · L1–L17 · step 028 of hello-playbook · diff · browse

[advisories]
version = 2

[licenses]
version = 2
# Exactly the licences this project actually needs. A longer list is not
# safer — it is a longer list of things you have stopped checking.
# Unicode-3.0: unicode-ident, through wasm-bindgen's macros (chapter 8).
allow = ["Apache-2.0", "GPL-3.0-or-later", "MIT", "Unicode-3.0"]

[bans]
multiple-versions = "warn"

# Every feature's dependencies, not only the default build's: an optional
# dependency is still shipped by whoever turns it on.
[graph]
all-features = true

The two exchanges above are not a picture of a session. bower verify builds this step, runs cargo run -q --example repl, types Ada and an empty line into it, and fails the book if the replies are not these. The prompt under them is the same Session, compiled to WebAssembly from this step's tree and running in your browser. In the epub and the PDF there is nothing to type into, so the transcript is all there is.
